# magnanix

My nix flake, using the denful pattern for NixOS, nix-darwin, and home-manager, using Determinate Nix.

Configuration is organised with [Den](https://github.com/denful/den), an aspect-oriented Nix framework: a
feature (an _aspect_) is written once and can configure `nixos`, `darwin` and `homeManager` together. Hosts
and users simply pick the aspects they want.

## Hosts

| Host         | Platform         | Kind       | User        | Notes                                                |
| ------------ | ---------------- | ---------- | ----------- | ---------------------------------------------------- |
| `magnus`     | `aarch64-darwin` | nix-darwin | `alberth`   | runs the darwintron VM                               |
| `darwintron` | `aarch64-darwin` | nix-darwin | `ephemeral` | [disposable Tart VM](#testing-changes-on-darwintron) |
| `nixostron`  | `x86_64-linux`   | NixOS      | `ephemeral` | [not buildable yet](#todo)                           |
| `muninn`     | `x86_64-linux`   | NixOS      | `alberth`   | headless server: SSH (keys only), UEFI, Attic cache, SMTP relay |

A host's name must match `scutil --get LocalHostName` (macOS) or
`hostname` (NixOS), so that `darwin-rebuild` / `nixos-rebuild` can find it. `base` sets the OS hostname from
`den.hosts.<system>.<host>.hostName`, which defaults to the host's name. A macOS host also sets its display name in
its `darwin` block, as `magnus` does with `networking.computerName = "Magnus"`. OS options like `networking` only
work inside a `darwin` or `nixos` block; at the top level of a host file they are flake-parts options and fail.

## Layout

`flake.nix` is **generated** by [flake-file](https://github.com/denful/flake-file); do not edit it. It loads every
module under `modules/` with [import-tree](https://github.com/denful/import-tree). The outputs are defined in
`modules/flake/outputs.nix`: the `darwinConfigurations` and `nixosConfigurations` that Den builds, plus the
`nh` wrappers, the flake-file generators, the dev shell and the formatter. Flake inputs are declared with
`flake-file.inputs.*` next to the aspect that uses them (see [Adding an input](#adding-an-input)).
Any file or directory whose name starts with `_` is ignored by import-tree.

The `base`, `determinate`, `sops` and `macos.homebrew` aspects are added to every host through `den.default.includes`.
Per-host settings go in `den.aspects.<host>`, and per-user settings in `den.aspects.<user>` (its `homeManager`
attribute is the user's Home Manager configuration).

### Features

The aspects in `modules/den/` apply to every host. Optional features live in `modules/packages/` and apply only
where something includes them. An aspect's name doesn't have to match its path (`modules/packages/tart.nix` defines
`den.aspects.tui.macos.tart`), so check the file for the name. An aspect that only does something on macOS has
`macos` as the next-to-last part of its name (`macos.mas`, `audio.macos.airfoil`), except the
[macOS defaults](#macos-defaults) under `darwin.*`, whose group name already says so. There are three places to
include one:

- `base` (`modules/den/base.nix`), for every host and user: the shells, macOS defaults, `attic.client`, `cliutils`, `imagemagick`,
  `mail`, `neovim`, `nix-tools`, `nushell`, `sudo`, `tzdata`, `tui.atuin`, `tui.tealdeer`, `tui.trash`, `tui.yazi`, `tui.yubikey` and
  `tui.zoxide`. NixOS hosts also get `fwupd`, `nixosKernel` and `systemdBoot` (systemd-boot, so the UEFI system
  partition must be mounted at `/boot`).
- The host's aspect, for apps on that machine. This is where `magnus` gets most of its apps:

  ```nix
  den.aspects.magnus.includes = [ den.aspects.browsers ];
  ```

  A host aspect delivers only its system-level config on its own. The `homeManager` parts reach the host's users
  only if the user includes `den.batteries.host-aspects`, as `alberth` and `ephemeral` do.

- The user's aspect, for what follows that user to every host, such as `gpg`:

  ```nix
  den.aspects.alberth.includes = [ den.aspects.gpg ];
  ```

A feature can target several classes at once. `gpg`, for example, sets Home Manager options (`homeManager`) and
installs the GPG Suite cask (`darwin`). Its Home Manager part reads the user's metadata, so it adapts to each user.

### User metadata

A user's aspect carries a `meta` attribute set. It is defined in a `let` binding in the user's file and exposed with
`inherit meta;`, so it can be used inside the aspect itself and read by features through
`den.aspects.<user>.meta`. `alberth` uses:

| Attribute        | Purpose                                                                               |
| ---------------- | ------------------------------------------------------------------------------------- |
| `username`       | the account name                                                                      |
| `fullName`       | display name for the OS account                                                       |
| `email`          | primary email address                                                                 |
| `authorizedKeys` | SSH public keys allowed to log in (all hosts)                                         |
| `gpgKey`         | long GPG key ID; sets `default-key` (optional)                                        |
| `gpgFingerprint` | full 40-character fingerprint of the key                                              |
| `gpgPublicKey`   | path to the exported public key (`.pub.asc`); imported with ultimate trust (optional) |

The `gpg` feature only sets `default-key` and imports a public key when `gpgKey` and `gpgPublicKey` exist, so users
without a GPG key still work. The `.pub.asc` file must be tracked by git for flakes to see it.
Export it with `gpg --export --armor <key-id> > modules/users/<user>/<key-id>.pub.asc`.

On macOS the `gpg` feature installs GPG Suite and keeps the Nix `gnupg` too. GPG Suite's installer puts its tools
on `PATH` through `/etc/paths.d/MacGPG2` and a `/usr/local/bin/gpg` symlink; the feature deletes both after every
activation (the symlink only if it points at GPG Suite) so the Nix `gpg` is not shadowed. The agent itself stays
GPG Suite's, and `gpg-agent.conf` and `dirmngr.conf` are left to GPG Suite; Home Manager only writes `gpg.conf`.

### Determinate Nix settings

`modules/den/determinate.nix` keeps the settings shared by every host (parallel evaluation and build-time flake
inputs) in one `sharedSettings` binding. nix-darwin takes them as `determinateNix.customSettings` and NixOS as
`nix.settings`; both end up in `/etc/nix/nix.custom.conf`. Put a setting in `sharedSettings` if it applies to all
hosts, or directly in the `darwin` / `nixos` block if it applies to one platform.

On macOS, Determinate owns the Nix installation, which switches nix-darwin's own `nix.*` management off
(`nix.enable = false`). Do not use `nix.gc`, `nix.optimise` or `nix.settings` in a `darwin` block; they have no
effect or fail an assertion. Use `determinateNix.customSettings` for Nix settings and
`determinateNix.determinateNixd.garbageCollector.strategy` for garbage collection instead.

### macOS defaults

`modules/packages/darwin/` holds one aspect per System Settings area, under `den.aspects.darwin.*`:
`controlCenter`, `finder`, `loginWindow`, `menuExtraClock`, `nsGlobalDomain`, `screencapture`,
`screenSaver`, `softwareUpdate` and `trackpad`. Each sets `system.defaults.*` through the `darwin` class (and
`CustomUserPreferences` for keys nix-darwin has no option for). `darwin.nix` bundles them as
`den.aspects.darwin.customizations`, which `base` includes, so they apply to every macOS host.

- `den.aspects.alberth.macos.dock` (`modules/users/alberth/dock.nix`) is the exception: it follows alberth rather
  than applying to every macOS host, so hosts without alberth keep the default Dock.
- `dock` and `screencapture` build paths such as `/Users/<name>/Downloads` from `system.primaryUser`, which each
  host sets with `den.batteries.primary-user`.
- `screencapture` creates its target directory (`~/Pictures/Screenshots/unsorted`) in a `postActivation` script,
  because nix-darwin doesn't and macOS ignores a missing location.
- The Dock's `persistent-apps` list is declarative: manual Dock changes are overwritten on the next switch.
  Orion comes from Home Manager (`~/Applications/Home Manager Apps`); Helium, Zed and Claude are Homebrew casks;
  iTerm is installed by hand.
- New files must be tracked by git (`git add`) before a plain `.#` flake reference can see them.

### OrbStack

`den.aspects.macos.orbstack` (`modules/packages/orbstack.nix`, included by `magnus`) installs OrbStack from nixpkgs
and keeps its containers and machines on their own APFS volume:

- On every switch (`extraActivation`), the `container-data-volume` script adds an APFS volume named
  `Container Data` to `disk3` (the internal container) if it doesn't exist yet, unlocks and mounts it at
  `/Volumes/Container Data` if needed, encrypts it if it isn't encrypted yet, and enables ownership on it. If this
  fails, for example because `disk3` isn't an APFS container, it prints a warning and the rest of the switch
  carries on.
- A `postActivation` script then creates `/Volumes/Container Data/OrbStack/<user>` (mode 700) for each of the
  host's users.
- Home Manager sets `data_dir` in `~/.orbstack/vmconfig.json` to that directory, keeping the file's other keys.
  This is the setting behind the app's Settings > Storage > Data location; `orb config` has no key for it.
  OrbStack picks it up the next time it starts.

The volume is FileVault-encrypted the same way the Nix installer encrypts the `Nix Store` volume: a random
passphrase is stored in the System keychain (account `Container Data`, service = the volume's UUID) before the
volume is encrypted with it. The volume is locked after every reboot, so the `org.nixos.container-data-volume`
launchd daemon runs the same script at boot to unlock and mount it (log: `/var/log/container-data-volume.log`).

> [!NOTE]
> After the first switch, the System keychain item (account `Container Data`) is the only copy of the volume's
> key. If it's deleted, the volume can't be unlocked and OrbStack's data on it is lost. Save the passphrase
> somewhere safe, such as 1Password:
>
> ```sh
> sudo security find-generic-password -a "Container Data" -w /Library/Keychains/System.keychain
> ```

Existing OrbStack data in `~/.orbstack/data` is not moved (activation warns if it exists).

### Fonts

`den.aspects.fonts` (`modules/packages/fonts.nix`) installs fonts through Home Manager's `home.packages`. Every
font is currently installed from nixpkgs, and nixpkgs is the preferred source for fonts. Use a Homebrew cask
(`homebrew.casks` in the aspect's `darwin` class) only for a font with no Nix package. Casks should be the
exception, not the rule.

## Applying the configuration

The configuration expects its live checkout at `~/Developer/magnanix` (the `magnanix.repoDir` default in
`modules/den/repo-dir.nix`): out-of-store symlinks such as Zed's `settings.json` point into it, and the
`deploy-magnanix` alias pulls there. Clone it there, or set `magnanix.repoDir` in a `homeManager` module for
that user or host.

Enter the dev shell and run the `apply-configuration` script. It picks the right command for the machine and
uses the machine's host name:

```sh
nix develop --command apply-configuration
```

- On macOS it runs `sudo darwin-rebuild switch --flake ".#$(scutil --get LocalHostName)"`.
- On NixOS it runs `sudo nixos-rebuild switch --flake ".#$(hostname)"`.

Each host also has an `nh` wrapper, for example `nix run .#magnus -- switch`.

`alberth`'s `deploy-magnanix` alias (`modules/users/alberth/shell-aliases.nix`) deploys the checkout at
`magnanix.repoDir`: it runs `git pull --ff-only` there, then the current host's `nh` wrapper with `switch`.
Deploy from `main` after CI passes; the alias pulls whichever branch is checked out.

To build without activating:

```sh
darwin-rebuild build --flake .#magnus      # macOS
nixos-rebuild build --flake .#nixostron    # NixOS
```

## Adding an input

Inputs are declared in the module that uses them, with `flake-file.inputs`, and `flake.nix` is generated from them:

1. Declare the input next to the aspect that needs it (or in its own file under `modules/`):

   ```nix
   flake-file.inputs.my-thing = {
     url = "github:someone/my-thing";
     inputs.nixpkgs.follows = "nixpkgs";   # only if it has a nixpkgs input
   };
   ```

2. Use it as `inputs.my-thing` in the same module, e.g. `darwin.imports = [ inputs.my-thing.darwinModules.default ];`.
3. `git add` any new file, then regenerate `flake.nix` and update the lock:

   ```sh
   nix run .#write-flake
   ```

   This also runs `flake-edit follow`, which keeps `follows` declarations in `flake.nix` deduplicated.
   To opt a nested input out, set `flake-file.inputs.<name>.inputs.<dep>.autoFollow = false;`
   (`determinate.nix` does this for Determinate's own `nix` input).

`nix flake check` fails if `flake.nix` is out of date with the modules. The dev shell enables
`.githooks/pre-commit` (`git config core.hooksPath .githooks`), which checks that staged `.nix` files are formatted
and that `nix run .#write-flake` leaves `flake.nix` and `flake.lock` unchanged. Skip it once with
`git commit --no-verify`.

## Updating inputs

The `Update flake inputs` workflow (`.github/workflows/update-flake-lock.yml`) runs every Saturday at 06:00 UTC,
or on demand from the Actions tab. It runs `nix flake update` and `nix run .#write-flake`, then opens or refreshes
a pull request from the `update-flake-lock` branch listing the inputs that changed. Before merging it, test it
on `magnus` with `darwintron-vm test update-flake-lock`.

Pull requests opened with the default `GITHUB_TOKEN` don't trigger other workflows. For CI to run on the update
PR, add a fine-grained personal access token limited to this repository, with read and write access to Contents
and Pull requests, as the `GH_TOKEN_FOR_UPDATES` repository secret. Without it, close and reopen the PR to start
CI.

## Binary cache

`muninn` runs an [Attic](https://github.com/zhaofengli/attic) binary cache server, from `den.aspects.attic.server`
(`modules/packages/attic.nix`). It serves port 8080 (open in `muninn`'s firewall) under two names:
`muninn.home.matos.cc` on the LAN and `muninn.ts.matos.cc` over Tailscale. It rejects requests addressed to any
other name, such as an IP address. The URLs it hands out (for `attic push`, for example) use whichever of the two
names the client used, so a client off the LAN can use the Tailscale name throughout. The data and its
SQLite database live in `/var/lib/atticd`. Objects that were neither pushed nor downloaded in the last 3 months
are garbage-collected.

The server signs its access tokens with `atticd_env` in `secrets/hosts/muninn.yaml`, an environment file that
sets `ATTIC_SERVER_TOKEN_RS256_SECRET_BASE64`. Replacing it invalidates every token issued with it. To rotate it,
generate a key with `openssl genrsa -traditional 4096 | openssl base64 -A` and paste it in with
`sops secrets/hosts/muninn.yaml`.

Caches and tokens are created with commands, not from the flake. After the first switch on `muninn`, run this
there once:

```sh
# An admin token; keep it in 1Password
atticd-atticadm make-token --sub alberth --validity "1y" \
  --pull '*' --push '*' --delete '*' --create-cache '*' --configure-cache '*' \
  --configure-cache-retention '*' --destroy-cache '*'

attic login muninn http://muninn.home.matos.cc:8080/ <admin-token>
attic cache create magnanix --public   # anyone on the LAN can pull; pushing needs a token
attic cache info magnanix              # prints the public key that clients trust
```

A machine that only pushes gets a narrower token (see [Pushing to the cache](#pushing-to-the-cache)).

### Using the cache

Every host pulls from the cache through `den.aspects.attic.client` (in `attic.nix`), which `base` includes. It
adds the cache to `extra-substituters` and its public key to `extra-trusted-public-keys`. The cache advertises
priority 41 and cache.nixos.org 40 (lower wins), so Nix still takes what cache.nixos.org has from there, and gets
the rest (unfree packages, the flake's own builds) from muninn. On macOS these land in `determinateNix.customSettings`, on NixOS in `nix.settings`;
both end up in `/etc/nix/nix.custom.conf`.

- **Server name:** `muninn.home.matos.cc` by default; the `tailscale` aspect switches it to
  `muninn.ts.matos.cc` through `local.attic.serverHost`, the same way it switches the mail relay.
- **Unreachable cache:** the client also sets `connect-timeout = 5`, so a host that can't reach muninn (off the
  LAN, or with Tailscale down) loses a few seconds rather than curl's default 300 s before Nix skips the cache.
  The setting applies to every substituter.
- **Recreating the cache** changes its signing key. Update `publicKey` in `attic.nix` with the output of
  `attic cache info magnanix`, or substitution from it fails signature checks.

Pulling needs no token because the cache is public. Pushing by hand (`attic push magnanix <path>`) needs
`attic login` with a push token on that machine.

### Pushing to the cache

`den.aspects.attic.push` (in `attic.nix`, included by `muninn` and `magnus`) runs `attic watch-store` as root,
which pushes every store path that becomes valid on the host, with its closure, to `magnanix`. That covers both
builds and downloads, but paths signed by cache.nixos.org are skipped, so in practice it pushes the host's own
builds and the unfree packages. On NixOS it is the `attic-watch-store` systemd service; on macOS it is the
`org.nixos.attic-watch-store` launchd daemon, which logs to `/var/log/attic-watch-store.log` (rotated by
`newsyslog`).

- **Server name:** the same `local.attic.serverHost` the host pulls from, so `muninn.ts.matos.cc` on both hosts.
  On muninn it reaches its own atticd through that name and starts after `atticd.service`.
- **Token:** `attic_push_token` in the host's `secrets/hosts/<host>.yaml`, decrypted to
  `/run/secrets/attic_push_token` (root only). The watcher's client config is generated in the Nix store and
  reads the token from that file, so nothing runs `attic login`, and the users' own `~/.config/attic` is
  untouched.
- **Server away:** if the server can't be reached when it starts, the watcher exits and is restarted: systemd
  backs off from 10 s to 10 min, launchd retries every minute. A rejected token doesn't stop it; each push
  fails with an error in the log (`journalctl -u attic-watch-store` on NixOS).
- **No token yet:** sops-nix fails the build when a declared secret is missing from its file, so the watcher and
  its secret only exist once the host's file has `attic_push_token`. Until then each build prints an
  `attic.push: no attic_push_token ...` warning, and the rest of the host builds and switches as usual.

To set it up for a host (`muninn` or `magnus`):

1. On muninn, mint a push token for the host:

   ```sh
   atticd-atticadm make-token --sub magnus --validity "1y" --pull magnanix --push magnanix
   ```

2. Add it to the host's secrets as `attic_push_token`, on its own line at the top level (just the token, no
   quotes or `Bearer`):

   ```sh
   sops secrets/hosts/magnus.yaml      # attic_push_token: <token>
   ```

3. Commit, and switch the host. The warning goes away and the watcher starts.

The token expires after a year. To replace it, mint a new one and repeat step 2. On NixOS the switch restarts
the watcher; on macOS restart it by hand with `sudo launchctl kickstart -k system/org.nixos.attic-watch-store`.

## Mail

Every host sends mail (cron output, `sendmail`, `mail`) through the network's SMTP smart relay, using
`den.aspects.mail` (`modules/packages/mail.nix`), which `base` includes. The relay is muninn, which passes the
mail on to Fastmail (see [The relay](#the-relay)). Other hosts only send; nothing on them listens for mail from the
network.

- **Relay:** `smtp.home.matos.cc`, or `smtp.ts.matos.cc` on hosts that include `den.aspects.tailscale` (`magnus`
  and `muninn`). The `tailscale` aspect makes the switch by setting `local.mail.relayHost`. Mail goes to port 25
  without authentication, using STARTTLS when the relay offers it. Both names are CNAMEs for muninn, managed
  outside this flake.
- **Addresses:** every sender address is rewritten to `alberth@matos.cc`, and local mail for `root` (and
  `postmaster`) is forwarded there.
- **NixOS** runs Postfix from `services.postfix`, with no `smtpd` on port 25 (except on the relay).
- **macOS** keeps Apple's Postfix. Each switch sets `relayhost`, `sender_canonical_maps`, `smtp_tls_security_level`
  and `alias_maps` in `/etc/postfix/main.cf` with `postconf -e` and leaves the rest of the file alone. A macOS update
  can reset `main.cf`; the next switch puts the keys back.

To test it, run `printf 'Subject: test\n\ntest\n' | sendmail root` and check that the queue is empty with `mailq`.
On NixOS, `journalctl -u postfix` shows why a message is stuck.

On macOS, the `tailscale` aspect installs the App Store app through `homebrew.masApps`, so you have to be signed in
to the App Store. On NixOS, log in to the tailnet once with `sudo tailscale up`.

### The relay

`den.aspects.mail.relay` (in `mail.nix`, included by `muninn`) turns the host's own Postfix into the relay:

- **Accepts** mail without authentication from the LAN (`10.0.4.0/22`), the tailnet (`100.64.0.0/10`,
  `fd7a:115c:a1e0::/48`) and the host itself, and relays it for no one else. It listens on port 25 (STARTTLS
  optional) and on port 465 (implicit TLS required). Both ports are open only on the interfaces in
  `local.mail.relay.interfaces` (`enp0s31f6` and `tailscale0` on muninn).
- **Rewrites** the envelope sender and `From:` header of everything it relays to `alberth@matos.cc`, including mail
  from devices like the printer, router and NAS, because Fastmail only accepts senders that are the account's
  identities.
- **Sends** everything, its own mail included, to `smtp.fastmail.com:465` with implicit TLS, checking Fastmail's
  certificate, and logs in as `alberth@matos.cc` with an app password.
- **Uses the `smtp.home.matos.cc` certificate for TLS** on both ports. It requests that certificate through
  `local.certbot.fqdns`, along with `smtp.ts.matos.cc`, so the host must include `certbot`. Clients connecting by
  either name get the `smtp.home.matos.cc` certificate. The Nix hosts don't check it, but a device on port 465 that
  verifies the name has to use `smtp.home.matos.cc`. Until certbot has issued the certificate, port 25 accepts
  mail without TLS (and logs a warning), and port 465 fails.

The app password is `fastmail_smtp_password` in `secrets/hosts/muninn.yaml`, which only muninn and the YubiKeys can
decrypt. sops-nix writes it into Postfix's SASL password table at `/run/secrets/rendered/postfix-sasl-passwords`
(root only) and restarts Postfix when it changes. To replace it, create a new app password in Fastmail's settings
(Privacy & Security), paste it in with `sops secrets/hosts/muninn.yaml`, and switch muninn.

## TLS certificates

`den.aspects.certbot` (`modules/packages/certbot.nix`, included by `magnus` and `muninn`) gets Let's Encrypt
certificates with certbot and the LuaDNS DNS plugin (`pkgs/python/certbot-dns-luadns.nix`), so a host needs no
open ports to prove it owns a name. A host lists its names in its `darwin` or `nixos` block:

```nix
local.certbot = {
  email = "alberth@matos.cc";   # required when fqdns isn't empty
  fqdns = [ "muninn.home.matos.cc" "muninn.ts.matos.cc" ];
};
```

`magnus` and `muninn` each request `<host>.home.matos.cc` and `<host>.ts.matos.cc`. The SMTP relay adds
`smtp.home.matos.cc` and `smtp.ts.matos.cc` on muninn.

- **Issuing:** a service started at boot (launchd on macOS, systemd on NixOS) requests each listed name that has no
  certificate yet, and retries every 15 minutes until all succeed. Names that already have one are skipped.
  A wildcard's certificate is named after its base domain, so `example.com` and `*.example.com` can't both be listed.
- **Renewing:** `certbot renew` runs daily (03:00 on macOS) and only renews certificates that are due.
- **Reading them:** certbot keeps its files in `/etc/letsencrypt`, readable only by root. After each issue or
  renewal, a hook copies the certificate and key to `/etc/letsencrypt-certs/<name>/`, owned by the primary user on
  macOS and readable by the `cert-readers` group (every normal user) on NixOS. Point services at those copies.

The LuaDNS credentials are `certbot_luadns` in `secrets/common.yaml`: an INI file with `dns_luadns_email` and
`dns_luadns_token`. A host using certbot must be a recipient of `common.yaml`.

To request a certificate by hand instead (it is only copied to `/etc/letsencrypt-certs` from its first renewal):

```sh
sudo certbot certonly --dns-luadns --dns-luadns-credentials /run/secrets/certbot_luadns -d example.com
```

## Adding a host

1. Copy `modules/hosts/_darwin_template.nix` or `_nix_template.nix` to `modules/hosts/<hostname>.nix`.
2. Replace `CHANGE_HOSTNAME` and `CHANGE_USERNAME`, and set the platform and `system.stateVersion`.
3. For secrets, add the host's age key (and the user's per-machine key) and a creation rule to `.sops.yaml`, then
   create `secrets/hosts/<hostname>.yaml`. No Nix change is needed: the `sops` aspect points each host at
   `secrets/hosts/<hostname>.yaml` by name.
4. Adjust the host's apps in `den.aspects.<hostname>` (see [Features](#features)). The templates start with a default
   set: `_1password`, `browsers`, `fonts`, `ghostty`, `audio` and `zed`, plus `bluetooth` on NixOS.
5. On NixOS, put the machine's generated `hardware-configuration.nix` next to the host file, in a
   `modules/hosts/<hostname>/` directory, as `_hardware-configuration.nix`. The leading `_` stops import-tree loading
   it as a flake module. Import it from the host's `nixos` block (see `muninn/muninn.nix`). The boot loader comes from `base`
   (`systemdBoot`).
6. New files must be tracked by git for flakes to see them (`git add` them).

## Adding a user

1. Copy `modules/users/_user_template/` to `modules/users/<username>/`.
2. Replace `CHANGE_USERNAME` and set `home.stateVersion`.
3. Add the user to a host with `den.hosts.<system>.<host>.users.<username> = { };`.
4. Include `den.batteries.host-aspects` if the user should get the `homeManager` parts of the host's apps.
5. Optionally add a `meta` set (see [User metadata](#user-metadata)) and include features from `modules/packages/`.
6. For secrets, add the user's per-machine age key and a creation rule to `.sops.yaml`, then create
   `secrets/users/<username>.yaml`.

## Secrets

Secrets are encrypted with [sops](https://github.com/getsops/sops) using age. `.sops.yaml` lists the recipients:

- one age-plugin-yubikey recipient per YubiKey,
- each machine's SSH host key converted to age (`ssh-to-age < /etc/ssh/ssh_host_ed25519_key.pub`),
- a per-machine age key for Home Manager (`age-keygen -y ~/.config/sops-nix/key.txt`).

`secrets/common.yaml` is for secrets shared between hosts (`magnus` and `muninn` can decrypt it),
`secrets/hosts/<host>.yaml` is per host, `secrets/users/<user>.yaml` is per user, and
`secrets/bootstrap/darwintron.yaml` holds darwintron's private keys. After changing the recipients, re-encrypt the existing files with
`sops updatekeys <file>`. The dev shell provides `sops`, `age`, `age-plugin-yubikey` and `ssh-to-age`.

sops only uses a YubiKey when it is given the key's age-plugin-yubikey identity, so the dev shell sets
`SOPS_AGE_KEY_CMD="age-plugin-yubikey --identity"`: every `sops` run asks the plugin for the identities of the
YubiKeys plugged in at the time. Outside the dev shell, add them to sops's key file instead (the identity only
points at the key on the YubiKey, so it isn't secret):

```sh
age-plugin-yubikey --identity >> "$HOME/Library/Application Support/sops/age/keys.txt"   # macOS
age-plugin-yubikey --identity >> ~/.config/sops/age/keys.txt                               # Linux
```

To create a file, write plaintext and encrypt it in place (`sops` can't open an empty file):

```sh
printf 'example: value\n' > secrets/common.yaml
sops encrypt --in-place secrets/common.yaml
sops secrets/common.yaml          # edit later; needs a YubiKey or the machine's key
```

### How secrets are wired

`modules/den/sops.nix` imports sops-nix for darwin, NixOS and Home Manager, and sets the defaults:

- **System:** each host's `sops.defaultSopsFile` is `secrets/hosts/<host>.yaml`, decrypted with the host's SSH
  key (`/etc/ssh/ssh_host_ed25519_key`).
- **Home Manager:** each user's `sops.defaultSopsFile` is `secrets/users/<user>.yaml`, decrypted with the key in
  `~/.config/sops-nix/key.txt`. Create it on each machine with `age-keygen -o ~/.config/sops-nix/key.txt` before
  the first switch.

Declare a secret in the aspect that uses it. Secrets in the per-host or per-user file need nothing more; secrets
from the common file need a `sopsFile`:

```nix
den.aspects.my-feature.os.sops.secrets.my_secret = { };
den.aspects.my-feature.os.sops.secrets.shared_secret.sopsFile = ../../secrets/common.yaml;
den.aspects.alberth.homeManager.sops.secrets.my_user_secret = { };
```

The decrypted value is at `config.sops.secrets.<name>.path`.

### alberth's password

`alberth`'s login password on NixOS is `alberth_password` in `secrets/common.yaml`, a yescrypt hash used as
`users.users.alberth.hashedPasswordFile`. It is declared with `neededForUsers`, so it is decrypted before the
accounts are created. Generate the hash with `nix shell nixpkgs#mkpasswd -c mkpasswd -m yescrypt` and paste
it in with `sops secrets/common.yaml`. Any NixOS host `alberth` is on must be a recipient of `common.yaml`.

The flake's password takes priority. `base` sets `users.mutableUsers = false` on every NixOS host, so each switch
resets the password and `passwd` can't change it. Every user on a NixOS host therefore needs a password option or
SSH keys; `ephemeral` has the throwaway password `ephemeral` and darwintron-vm's access key. macOS passwords are never managed here: nix-darwin has no password option, and
changing one with `dscl` breaks the login keychain and the FileVault token.

## Testing changes on darwintron

`darwintron` is a disposable [Tart](https://tart.run) VM on `magnus` for trying a change before it lands. It is
deliberately minimal: to test something, add its aspect to `modules/hosts/darwintron.nix` on a branch. Its primary
user is `ephemeral`, whose secrets hold fake values, and it can't read `common.yaml` or `alberth.yaml`.

Run these inside `nix develop` on `magnus`. Only committed code is tested.

```sh
darwintron-vm seed                # once: macOS, Determinate Nix and the ephemeral user
darwintron-vm baseline            # after main moves: the seed with main applied
darwintron-vm test my-branch      # switch a clone to my-branch, check, reboot, roll back, delete
darwintron-vm test my-branch --fresh   # from the seed, as a first install (nothing to diff or roll back)
darwintron-vm test my-branch --keep    # keep the VM afterwards; then `ssh` and `destroy`
```

A failed test keeps its VM for inspection. `darwintron-vm ssh` opens a shell on it and `darwintron-vm destroy`
deletes it. Each test checks the canary secrets, the login shell and the hostname, and prints an `nvd` diff when
starting from the baseline.

The VM keeps one identity however often it is rebuilt. `secrets/bootstrap/darwintron.yaml` holds its private keys,
encrypted to the YubiKeys and `alberth_magnus`. The script decrypts them on `magnus`, pipes them in over SSH before
activation, and removes them before saving an image, so neither image contains them. The public halves are
`host_darwintron` and `ephemeral_darwintron` in `.sops.yaml`.

The image is pinned by digest at the top of `pkgs/darwintron-vm.sh`. YubiKeys, 1Password, the App Store and audio
hardware can't be tested in the VM.

## Shells

Shell configuration lives in `modules/packages/shells/`, one aspect per shell plus shared pieces. The `base` aspect
includes `shell.zsh`, `shell.fish` and `shell.bash`, so every host and user gets all three:

```nix
den.aspects.base.includes = [ den.aspects.shell.bash den.aspects.shell.fish den.aspects.shell.zsh ];
```

| Aspect                 | File                        | What it does                                                                                |
| ---------------------- | --------------------------- | ------------------------------------------------------------------------------------------- |
| `shell.zsh`            | `zsh.nix`                   | Home Manager `programs.zsh`                                                                 |
| `shell.fish`           | `fish.nix`                  | Home Manager `programs.fish`, plus system-level fish on NixOS and macOS                     |
| `shell.bash`           | `bash.nix`                  | Home Manager `programs.bash`                                                                |
| `shell.starship`       | `starship.nix`              | Home Manager `programs.starship` with a default `starship.toml`; the prompt for every shell |
| `shell.shellAliases`   | `shell-aliases.nix`         | aliases shared by the shells, and per-OS `environment.shellAliases`                         |
| `shell.posixFunctions` | `shell-functions-posix.nix` | shared functions for zsh and bash                                                           |
| `shell.fishFunctions`  | `shell-functions-fish.nix`  | the same functions, written for fish                                                        |

Each shell aspect includes the aliases, functions and `shell.starship` aspects it needs.

**Login shell.** `alberth`'s login shell is Nix's zsh on every host, set in `modules/users/alberth/alberth.nix`
(`shell.zsh` also enables `programs.zsh` at system level, which the setting requires). `ephemeral` does the same in
its own file:

- **NixOS:** `users.users.alberth.shell = pkgs.zsh`. This overrides the fish default that `shell.fish` sets with
  `users.defaultUserShell`.
- **macOS:** nix-darwin only applies `users.users.<name>.shell` to users in `users.knownUsers`, and listing
  `alberth` there would make nix-darwin manage (and possibly delete) the account. So the config adds Nix's zsh
  to `/etc/shells` (`environment.shells`) and sets the shell on the existing account with `dscl` in a
  `postActivation` script. It runs after every activation and only changes the shell if it differs. Open a new
  terminal after the first switch for it to take effect.
  Check it with `dscl . -read /Users/alberth UserShell`; it should be `/run/current-system/sw/bin/zsh`.

- **zsh:** config lives in `$XDG_CONFIG_HOME/zsh`. oh-my-zsh is enabled with its theme turned off, because
  Starship draws the prompt. The history file is
  `~/.local/share/zsh/history`, effectively unlimited and shared between sessions. Plugins load in this order:
  `fzf-tab` (must be first), `zsh-autosuggestions`, `zsh-syntax-highlighting`, `zsh-history-substring-search`,
  `you-should-use`. On Linux the `fzf-tab` native module is stripped so it falls back to pure zsh. A glibc
  mismatch stops the prebuilt module loading on non-NixOS hosts, and the fallback avoids that. `envExtra` sources
  the Nix daemon profile, so `nix` is on `PATH` when zsh is the login shell on non-NixOS Linux.
- **fish:** Home Manager enables fish integration, turns off the greeting, and installs the `autopair` and `bass`
  plugins. Fish is also enabled at system level on NixOS (where it becomes the default user shell) and on macOS.
  OS-specific aliases and functions live next to that (xclip clipboard aliases and PulseAudio and DNS resets on
  NixOS; `pbcopy` aliases and `tail-exit-node-fix` on macOS).
- **Starship prompt:** the shell indicator is on, so each prompt shows which shell you're in: 🐚 bash, 🦓 zsh,
  🐟 fish, 🪟 PowerShell, and ❓ for anything else. The hostname is trimmed at the first `.` (`host.example.com`
  shows as `host`).
- **Nushell:** `programs.nushell` writes `config.nu` and `env.nu` (in `~/Library/Application Support/nushell` on
  macOS), so the atuin, direnv, starship, yazi and zoxide integrations load in it too. `loadSessionVariables` loads
  the Home Manager session variables (such as `EDITOR`) when Nushell starts without them, for example as the
  shell a terminal opens directly.
- **1Password CLI:** zsh and fish both load `$XDG_CONFIG_HOME/op/plugins.sh` if it exists (fish through `bass`).
  The `_1password` aspect adds `op` completions to bash, zsh and fish, so they only load on hosts that include it.
- **Aliases and functions:** the common aliases (`rm`/`mv`/`cp` with `-i`, the `ssh*` variants, `git-log`,
  `git-author`) apply to zsh and fish. The functions cover GPG and YubiKey resets, Docker cleanup, Tailscale
  and DNS fixes, network info, and a zoxide and fzf directory jumper (`zox`). They are written once for POSIX
  shells and once for fish, so keep the two files in step when adding or changing one. In `shell-functions-posix.nix`
  each entry becomes a shell function; in `shell-functions-fish.nix` it becomes a fish function.

## Neovim

`den.aspects.neovim` (`modules/packages/neovim.nix`, included by `base`) installs Neovim with
[LazyVim](https://www.lazyvim.org) on every host, through the [lazyvim-nix](https://github.com/pfassina/lazyvim-nix)
Home Manager module, and sets `EDITOR=nvim`. `vi`, `vim` and `vimdiff` run Neovim too.

- **From Nix, not the network:** plugins, Treesitter parsers, language servers and formatters are all built by
  Nix, and Mason is disabled, so Neovim starts offline and works on NixOS. A few specs in the aspect fill gaps in
  lazyvim-nix that would otherwise make lazy.nvim clone plugins from GitHub at startup (lazy.nvim itself,
  `friendly-snippets`, `catppuccin`). Nix owns the config, so changes made through `:LazyExtras` don't persist; enable
  extras with `programs.lazyvim.extras` instead. LazyVim's version comes from the `lazyvim-nix` input in `flake.lock`.
- **Languages:** the `lang.nix`, `json`, `markdown`, `toml` and `yaml` extras. Tools that lazyvim-nix doesn't map to
  a package (such as `yaml-language-server`, `marksman` and `lua-language-server`) are listed in `extraPackages`;
  with Mason disabled, a missing language server is an error whenever a file of its type opens.
- **`EDITOR` and `VISUAL`:** the aspect sets only `EDITOR`. Hosts with Zed set `VISUAL=zed --wait`
  (`modules/packages/zed/zed.nix`), and most programs (git, crontab, ...) prefer `VISUAL`, so on those hosts they
  open Zed. Elsewhere `VISUAL` is unset and they use Neovim. Home Manager's `programs.neovim.defaultEditor` stays off
  because it would also set `VISUAL`, and the two definitions would fail evaluation.
- **Theme:** users with `magnanix.draculaPro` get Dracula PRO, loaded at runtime from the checkout (never copied
  into the store): `dracula-pro` on a dark terminal and `dracula-pro-alucard` on a light one, following the
  `background` Neovim detects from the terminal at startup. Everyone else, and hosts without the checkout, get the
  free Dracula theme. Neovim doesn't add itself to `draculaPro.usedBy`, so it never triggers the clone, which keeps
  headless hosts like muninn from trying. Clone the checkout there by hand to get Dracula PRO in Neovim.

## Direnv

`.envrc` contains `use flake`, so with [direnv](https://direnv.net) the dev shell loads automatically in this
directory (run `direnv allow` once). The `direnv` feature (`modules/packages/direnv.nix`, included by `alberth`)
installs direnv through Home Manager with nix-direnv and shell integration enabled.

`.envrc` also sets `NIX_SENTRY_ENDPOINT=""` before `use flake`. Determinate Nix starts a Crashpad-based Sentry
crash reporter, which aborts on macOS inside sandboxes that deny Mach service registration (for example agent
terminals), with `bootstrap_check_in ... Permission denied (1100)`. An empty endpoint disables the reporter, so
`nix` runs normally. The side effect is that Determinate no longer receives Nix crash reports from this directory.
Outside direnv, prefix the command instead: `NIX_SENTRY_ENDPOINT= nix ...`.

## Continuous Integration

magnanix uses [GitHub Actions](https://docs.github.com/en/actions) to automatically build the flake outputs across three platforms and cache the results in muninn's Attic binary cache server.

### The build.yml workflow

[`.github/workflows/build.yml`](.github/workflows/build.yml) runs on every push to `main` and on pull requests (including PRs from forks). It builds:

- **aarch64-darwin:** `darwinConfigurations.magnus` and `darwinConfigurations.darwintron` (system closures)
- **x86_64-linux:** `nixosConfigurations.muninn` (system closure)
- **aarch64-linux:** `devShells.aarch64-linux.default` (development shell; full system builds deferred)

Each job:
1. Joins the Tailscale network via **Workload Identity Federation** (ephemeral GitHub OIDC token)
2. Authenticates to the Attic cache with a scoped CI token
3. Configures Nix to use the cache as a substituter
4. Builds the assigned flake output
5. Pushes results back to the cache via `attic watch-store`

**For main-branch pushes:** Build outputs are cached on muninn and available to all machines for substitution.

**For pull requests:** Builds run the same way, but:
- PRs from the main repo (not forks) can push to the cache
- PRs from forks do not push (extra safety; OIDC token is still scoped)

### Runners

All runners are GitHub-hosted (no self-hosted infrastructure):

| Platform       | Runner                | Cost        | Notes                                         |
|---|---|---|---|
| aarch64-darwin | `macos-26`            | Free*       | 3 vCPU Apple M1, 7 GB RAM. ~40–60 min.       |
| x86_64-linux   | `ubuntu-latest`       | Free        | 4 vCPU, 16 GB RAM. ~10–20 min.               |
| aarch64-linux  | `ubuntu-24.04-arm`    | Free        | 4 vCPU Graviton, 16 GB RAM. ~5–10 min.       |

*Public repos have no GitHub Actions multiplier on macOS runners.

### Cache security

- **Ephemeral tokens:** GitHub's OIDC token is valid only ~5 minutes per workflow run and cannot be reused.
- **Scoped network access:** Tailscale ACL restricts `tag:ci` to `muninn.ts.matos.cc:8080` only.
- **Scoped Attic token:** CI token can only pull and push to the `magnanix` cache, with 1-year TTL.

### Setup & troubleshooting

See [TAILSCALE_SETUP.md](documentation/TAILSCALE_SETUP.md) for detailed instructions on enabling GitHub Actions to access the cache. The setup requires:
- A Tailscale OIDC credential (subject wildcard: `repo:amatos:367718/magnanix@1435869087:*`)
- Three GitHub Action secrets: `TS_OAUTH_CLIENT_ID`, `TS_AUDIENCE`, `ATTIC_TOKEN`
- An ACL rule allowing `tag:ci → muninn:8080` (kept in [`documentation/tailscale-policy/acl.hujson`](documentation/tailscale-policy/acl.hujson))

Don't add a top-level directory named `tailscale/`. On macOS runners, `tailscale/github-action` builds Tailscale from
source by cloning it into `./tailscale` inside the checkout, and the darwin job fails with "destination path
'tailscale' already exists" if that path is taken.

The darwin job also resets the runner's DNS right after joining the tailnet. On macOS the action points system DNS
at MagicDNS (`100.100.100.100`), which fails to resolve public names on hosted runners
([tailscale/github-action#315](https://github.com/tailscale/github-action/issues/315)). That's safe because
`muninn.ts.matos.cc` is in public DNS, so CI doesn't need MagicDNS to find it.
