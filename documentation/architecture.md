# Architecture

## Layout

`flake.nix` is **generated** by [flake-file](https://github.com/denful/flake-file); do not edit it. It loads every
module under `modules/` with [import-tree](https://github.com/denful/import-tree). The outputs are defined in
`modules/flake/outputs.nix`: the `darwinConfigurations` and `nixosConfigurations` that Den builds, plus the
`nh` wrappers, the flake-file generators, the dev shell and the formatter. Flake inputs are declared with
`flake-file.inputs.*` next to the aspect that uses them (see [Adding an input](#adding-an-input)).
Any file or directory whose name starts with `_` is ignored by import-tree.

```
flake.nix                      GENERATED by flake-file (`nix run .#write-flake`); do not edit
flake.lock                     pinned inputs
.envrc                         direnv: `use flake` (loads the dev shell), disables Nix's Sentry reporter
.githooks/pre-commit           formatting and flake.nix up-to-date checks (enabled by the dev shell)
.github/workflows/             CI and the weekly flake input update PR (see ci.md, applying.md)
.github/actions/attic-cache/   composite action that joins Tailscale and sets up the Attic cache for CI
.sops.yaml                     sops recipients and creation rules
secrets/                       encrypted secrets: common, per host, per user, and the test VMs' bootstrap keys
documentation/                 this documentation, plus CICD_PLAN.md, TAILSCALE_SETUP.md and the tailnet ACL policy
pkgs/                          the darwintron-vm / nixostron-vm scripts and locally packaged software
modules/
├── den/                       the framework and what every host shares: base, Determinate Nix, sops, Homebrew,
│                              Home Manager integration, disko, magnanix.repoDir and magnanix.draculaPro options,
│                              and _versions.nix (the branch each core input tracks)
├── flake/outputs.nix          the flake's outputs: configurations, nh wrappers, checks, dev shell, formatter
├── packages/                  opt-in aspects that hosts, users or `base` include, one feature per file
│   ├── appstore/              Mac App Store apps, one aspect per app or group of apps
│   ├── darwin/                macOS System Settings, one aspect per settings area
│   ├── hyprland/              Hyprland and its interchangeable desktop shells
│   ├── languages/             one aspect per programming language
│   ├── shells/                zsh, fish, bash, Starship, and the aliases and functions they share
│   └── ...                    everything else (browsers/, TeX/, audio/, 1password/, zed/, ...)
├── hosts/                     one directory per host, plus templates/ (new-host templates) and virtual/ (test VMs)
└── users/                     one directory per user, plus _user_template/
```

Every `.nix` file starts with a header naming the aspect(s) it defines, the platforms it configures
(`nixos`, `darwin`, `home-manager`) and what it is for, followed by notes on anything that differs from the
defaults. Read the header first when you need to know what a file does or why something is set.

The `base`, `determinate`, `sops` and `macos.homebrew` aspects are added to every host through `den.default.includes`.
Per-host settings go in `den.aspects.<host>`, and per-user settings in `den.aspects.<user>` (its `homeManager`
attribute is the user's Home Manager configuration).

## Features

The aspects in `modules/den/` apply to every host. Optional features live in `modules/packages/` and apply only
where something includes them. An aspect's name doesn't have to match its path (`modules/packages/tart.nix` defines
`den.aspects.tui.macos.tart`), so check the file for the name. An aspect that only does something on macOS has
`macos` as the next-to-last part of its name (`macos.mas`, `audio.macos.airfoil`), except the
[macOS defaults](macos.md#macos-defaults) under `darwin.*`, whose group name already says so. There are three places to
include one:

- `base` (`modules/den/base.nix`), for every host and user: the shells, macOS defaults, `attic.client`, `cli.fastfetch`, `cli.imagemagick`,
  `cli.tealdeer`, `cli.trash`, `cli.utils`, `cli.yubikey`, `cli.zoxide`, `git`, `mail`, `nix-tools`, `python`, `sudo`, `tzdata`, `tui.atuin`, `tui.neovim`,
  `tui.yazi` and `tui.zellij`. NixOS hosts also get `cli.fwupd`, `nixosKernel` and `systemdBoot` (systemd-boot, so the UEFI system
  partition must be mounted at `/boot`).
- The host's aspect, for apps on that machine. This is where most desktop apps are included:

  ```nix
  den.aspects.<host>.includes = [ den.aspects.browsers ];
  ```

  A host aspect delivers only its system-level config on its own. The `homeManager` parts reach the host's users
  only if the user includes `den.batteries.host-aspects`, as `alberth` and `ephemeral` do.
  The other way round, every host takes the system-level parts (`os`, `nixos`, `darwin`) of its users'
  aspects, because `modules/den/base.nix` adds `den.batteries.user-aspects` to every host.

- The user's aspect, for what follows that user to every host, such as `gpg`:

  ```nix
  den.aspects.alberth.includes = [ den.aspects.gpg ];
  ```

- The host's `provides.<user>`, for what one user gets on some hosts but not others. `alberth`'s heavier sets
  are opted into this way: `alberth.dev` (language toolchains and `gh`) on magnus and fortuna,
  `alberth.macDesktop` (Dock and Mac apps) on magnus and `alberth.mail` on magnus and fortuna. muninn and
  tenabrae, being headless, take none of them:

  ```nix
  den.aspects.<host>.provides.alberth.includes = [ den.aspects.alberth.dev ];
  ```

A feature can target several classes at once. `gpg`, for example, sets Home Manager options (`homeManager`) and
installs the GPG Suite cask (`darwin`). Its Home Manager part reads the user's metadata, so it adapts to each user.

## User metadata

A user's aspect carries a `meta` attribute set. It is defined in a `let` binding in the user's file and exposed with
`inherit meta;`, so it can be used inside the aspect itself and read by features through
`den.aspects.<user>.meta`. `alberth` uses:

| Attribute        | Purpose                                                                               |
| ---------------- | ------------------------------------------------------------------------------------- |
| `username`       | the account name                                                                      |
| `fullName`       | display name for the OS account and git's `user.name`                                 |
| `email`          | primary email address and git's `user.email`                                          |
| `authorizedKeys` | SSH public keys allowed to log in (all hosts)                                         |
| `gpgKey`         | long GPG key ID; sets `default-key` and git's signing key (optional)                  |
| `gpgFingerprint` | full 40-character fingerprint of the key                                              |
| `gpgPublicKey`   | path to the exported public key (`.pub.asc`); imported with ultimate trust (optional) |

The `gpg` feature only sets `default-key` and imports a public key when `gpgKey` and `gpgPublicKey` exist, so users
without a GPG key still work. The `.pub.asc` file must be tracked by git for flakes to see it.
Export it with `gpg --export --armor <key-id> > modules/users/<user>/<key-id>.pub.asc`.

On macOS the `gpg` feature installs GPG Suite and keeps the Nix `gnupg` too. GPG Suite's installer puts its tools
on `PATH` through `/etc/paths.d/MacGPG2` and a `/usr/local/bin/gpg` symlink; the feature deletes both after every
activation (the symlink only if it points at GPG Suite) so the Nix `gpg` is not shadowed. The agent itself stays
GPG Suite's, and `gpg-agent.conf` and `dirmngr.conf` are left to GPG Suite; Home Manager only writes `gpg.conf`.

## Determinate Nix settings

`modules/den/determinate.nix` keeps the settings shared by every host (parallel evaluation and build-time flake
inputs) in one `sharedSettings` binding. nix-darwin takes them as `determinateNix.customSettings` and NixOS as
`nix.settings`; both end up in `/etc/nix/nix.custom.conf`. Put a setting in `sharedSettings` if it applies to all
hosts, or directly in the `darwin` / `nixos` block if it applies to one platform.

On macOS, Determinate owns the Nix installation, which switches nix-darwin's own `nix.*` management off
(`nix.enable = false`). Do not use `nix.gc`, `nix.optimise` or `nix.settings` in a `darwin` block; they have no
effect or fail an assertion. Use `determinateNix.customSettings` for Nix settings and
`determinateNix.determinateNixd.garbageCollector.strategy` for garbage collection instead.

## Adding an input

Inputs are declared in the module that uses them, with `flake-file.inputs`, and `flake.nix` is generated from them:

1. Declare the input next to the aspect that needs it (or in its own file under `modules/`):

   ```nix
   flake-file.inputs.my-thing = {
     url = "github:someone/my-thing";
     inputs.nixpkgs.follows = "nixpkgs";   # only if it has a nixpkgs input
   };
   ```

2. Use it as `inputs.my-thing` in the same module, e.g. `darwin.imports = [ inputs.my-thing.darwinModules.default ];`.
3. `git add` any new file, then regenerate `flake.nix` and update the lock:

   ```sh
   nix run .#write-flake
   ```

   This also runs `flake-edit follow`, which keeps `follows` declarations in `flake.nix` deduplicated.
   To opt a nested input out, set `flake-file.inputs.<name>.inputs.<dep>.autoFollow = false;`
   (`determinate.nix` does this for Determinate's own `nix` input).

`nix flake check` fails if `flake.nix` is out of date with the modules. The dev shell enables
`.githooks/pre-commit` (`git config core.hooksPath .githooks`), which checks that staged `.nix` files are formatted
and that `nix run .#write-flake` leaves `flake.nix` and `flake.lock` unchanged. Skip it once with
`git commit --no-verify`.

## Channel versions

The branch or tag of the four core inputs is set in one place, `modules/den/_versions.nix`, so they can be moved
between unstable and stable together:

| Input          | Declared in                    | Current            | Stable form           |
| -------------- | ------------------------------ | ------------------ | --------------------- |
| `nixpkgs`      | `modules/den/flake-file.nix`   | `nixpkgs-unstable` | `nixos-YY.MM`         |
| `home-manager` | `modules/den/home-manager.nix` | `master`           | `release-YY.MM`       |
| `nix-darwin`   | `modules/den/nix-darwin.nix`   | `master`           | `nix-darwin-YY.MM`    |
| `determinate`  | `modules/den/determinate.nix`  | `main`             | a tag, e.g. `v3.24.2` |

The input declarations (and their `follows` settings) stay in the files listed; they only read the ref with
`import ./_versions.nix`. The file starts with `_`, so import-tree does not load it as a module. nixpkgs,
home-manager and nix-darwin must be on matching releases, so change all three at once, then run
`nix run .#write-flake`. The Nix version itself comes from the `determinate` input.

All inputs are fetched from GitHub. Determinate's own nested inputs (`nix`, its nixpkgs mirror, `flake-parts`,
`git-hooks-nix`) still come from FlakeHub, because Determinate's flake declares them that way and `nix` has to
match the Determinate release.

`stateVersion` is deliberately not in `_versions.nix`: it is set per host and per user at install time and does
not change when the channels do.

## Formatting

The formatter is `nixfmt` (the RFC 166 style), also used to format the generated `flake.nix`:

```sh
git ls-files -z '*.nix' | xargs -0 -r nix fmt                                    # format
git ls-files -z '*.nix' | xargs -0 -r nix develop --command nixfmt --check       # check
```
